## Maker brief: security review, fuzzing and hardening of the merged crates

Scope: everything on develop EXCEPT crates/caparra-gate and crates/bnap-carrier-http (another session is still building those; do not edit them). Focus on the money path and parsers: bnap-core, bnap-plug, bnap-signer-file, bnap-signer-process, bnap-store-sqlite, bnap-store-postgres, bnap-scheme-notes, bnap-scheme-l402, bnap-scheme-mpp, bnap-rail-*, bnap-scheme-dpop, bnap-scheme-webbotauth, bnap-carrier-mcp, caparra-wallet, bnap-cli, bnap-mcp.

1. Fuzzing: add a `fuzz/` cargo-fuzz workspace (excluded from the main workspace, nightly only) with targets for every parser that takes untrusted bytes: TLV/BigSize, Offer, Credential, Response, manifest JSON (incl. duplicate keys), the notes body/witness, L402 token/macaroon, MPP credential JSON, DPoP JWT, Web Bot Auth signature input, MCP _meta credential, the signer IPC frames. Run each target for at least 10 minutes (cargo +nightly fuzz run <t> -- -max_total_time=600); every crash becomes a minimized regression test in the owning crate plus a fix. Add a scheduled (weekly) CI workflow `.github/workflows/fuzz.yml` that runs each target briefly.
2. Deep review with independent lenses: spawn THREE separate reviewer agents (Agent tool) in parallel, each with one lens and no access to the others' output: (a) money path: double spend, cap/change/refund over-issue, rail amount/unit/finality trust, store atomicity, replay vs SPENT, pending timeout; (b) cryptography and parsing: signature malleability (ECDSA low-S, Ed25519 strict), tagged-hash domain separation, canonical encodings, constant-time MAC/HMAC compares, duplicate JSON keys, size limits, integer overflow; (c) secrets and operations: key file permissions, zeroize, logging/Debug leaks of keys, mnemonics, macaroons, preimages and tokens, socket permissions, timeouts and DoS (unbounded maps, allocation from length prefixes). Each returns findings with severity, file:line and a reproduction.
3. For every HIGH/MEDIUM finding: write a test that fails, fix, commit, push. Then a fresh independent checker verifies each fix bites (break it, see the test fail, revert) and looks for regressions. Up to 3 rounds.
4. LOW findings and anything you defer: write them to `notes/b5-security.md` as a table (id, crate, severity, file:line, description, suggested fix) so the orchestrator can file them as GitHub issues.
5. Write `SECURITY-REVIEW.md` at the repo root: scope, method, lenses, fuzz targets and hours, findings by severity with status, known limitations.
